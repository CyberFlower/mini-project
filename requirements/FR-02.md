# FR-02: 요구사항 개요와 세부 문서

개요: [요구사항](../REQUIREMENTS.md)

## Acceptance Criteria

- 확정된 요구사항과 가정을 구분하고, 중요한 모호함은 관련 구현 전에 확인한다.
- `0. 용어`, `1. Goal & Scope`, `2. Functional Requirements`, `3. Non-functional Requirements`, `4. Constraints` 순서를 유지한다.
- 기능 요구사항에 고유 ID와 개별 `Acceptance Criteria`가 있다. 모든 규칙은 ID가 있는 요구사항 안에 둔다.
- 개요의 요구사항마다 제목·Feature·한 문장 요약을 둔다. Acceptance Criteria가 5개 항목 이하이고 표·다이어그램·근거가 없으면 개요에 그대로 두고, 그보다 길면 요약 뒤에 세부 파일 링크만 둔다. 같은 요구사항은 개요와 세부 파일 중 한 곳에만 둔다.
- 세부 파일은 Acceptance Criteria, 다이어그램, 근거 순으로 쓰고 한 문장 요약을 반복하지 않는다. 다이어그램·근거는 필요할 때만 두고, 근거에는 이유·참고 자료만 쓴다. 동작을 제한하는 문장은 Acceptance Criteria에 둔다.
- 미확정 사항이 있을 때만 `Open Questions`를 추가하고, 해결하면 해당 본문에 반영한다.
- 필요한 비기능 요구사항이나 제약이 없으면 억지로 추가하지 않고 현재 없음을 표시한다.

## 근거

- 개요만 읽어도 전체 요구사항을 볼 수 있고, 작업할 때는 관련 세부 파일만 읽으면 된다. 짧은 요구사항까지 파일로 나누면 파일만 늘어나므로 개요에 둔다.
- 규칙의 이유를 규칙 옆(세부 파일의 근거)에 두면 규칙이 바뀔 때 함께 고친다. 이전에는 Feature `DESIGN.md`에 두었다.
- 세부 파일을 `docs/`가 아닌 루트 `requirements/`에 두는 이유: 이 저장소처럼 `docs/`를 배포에서 빼는 프로젝트에서도 요구사항 원본이 함께 배포된다.
