# FR-03: Feature 정제와 구조·구현 문서

개요: [요구사항](../REQUIREMENTS.md)

## Acceptance Criteria

- 하나의 사용자 목적을 완성하고 검증할 수 있는 요구사항들을 Feature로 묶고, 다음에 구현할 Feature부터 정제한다.
- 루트 `ARCHITECTURE.md`에는 구성 요소·역할·외부 시스템·입출력과 구조의 선택 이유를 둔다. 첫 Feature의 구조를 정할 때 만들고, 구성 요소나 연결이 바뀔 때 갱신한다.
- Feature별로 `docs/features/<feature>/IMPLEMENTATION.md`를 유지하고, 관련 요구사항 ID, 구현 순서·상태와 실제 검증 결과를 기록한다.
- 다이어그램은 Mermaid로 글로 읽기 어려울 때만 두고, 같은 규칙을 글·표·그림으로 중복하지 않는다. 규칙 그림은 요구사항 세부 파일에, 구조 그림은 `ARCHITECTURE.md`에 둔다. 구성 요소가 하나면 구조 그림을 두지 않는다.
- 요구사항 전문과 Acceptance Criteria 정의는 복사하지 않고 원본을 참조한다.
- 기존 설계·구현 기록은 새 위치로 이동하면서 보존하고 링크를 갱신한다. 이전 형식의 Feature `DESIGN.md`는 규칙의 이유를 요구사항 근거로, 구조와 그 이유를 `ARCHITECTURE.md`로 옮긴 뒤 삭제한다.
- 아직 결정되지 않은 Feature의 빈 문서를 미리 만들지 않는다.

## 근거

- 전체 범위를 확인하면서 현재 Feature의 문서만 읽을 수 있도록 Feature 문서를 나눈다.
- 구조는 Feature보다 오래 유지되고 여러 Feature가 함께 쓴다. Feature마다 설계 문서를 두면 같은 구조가 여러 곳에 적히므로 루트 `ARCHITECTURE.md` 하나에 둔다.
- 이전 설계 템플릿은 다이어그램을 우선해 표현하도록 안내했다. 그림과 글이 같은 규칙을 함께 담으면 한쪽만 고쳐질 수 있어, 글로 읽기 어려울 때만 그림을 둔다.
